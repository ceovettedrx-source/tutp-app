## TUT-88: `scripts/release-gate.ps1 <revision> <commit>`

Files: `scripts/release-gate.ps1` (thin: gathers facts, prints), `scripts/lib/release-gate-logic.ps1` (pure checks, no network), `tests/unit/release-gate.test.js` (runs the logic through PowerShell with fixture facts), `CLAUDE.md` (two rules, see end).

Facts gathered (all read-only, names only): live revision = the 100 % entry of `status.traffic`; labels via `--format="value(metadata.labels.commit-sha)"`; env via `--format=flattened(spec.containers[0].env)` read into memory, only NAMES and the two flag values are kept, nothing else is ever printed; never `--format=json`; commit status via `gh api repos/<repo>/commits/<commit>/status`, context `e2e`.

Checks, each prints `PASS n` or `FAIL n: reason`; all five always run so the founder sees every failure at once:
1. Live commit-sha label is an ancestor of `<commit>` (`git merge-base --is-ancestor`). Missing label, or a commit git does not know = FAIL.
2. Env and secret names: any name only on live = FAIL. (Names only on the new revision are listed, not failed.)
3. `ANSWER_V2_ENABLED` and `IMAGE_GEN_ENABLED` have the same value on both (absent on both = same; absent on one = FAIL).
4. `E2E_REPLAY` is absent on the new revision.
5. Commit status `e2e` on `<commit>` is `success` (none, pending, failure = FAIL).

Only if all five pass it prints the one line `gcloud.cmd run services update-traffic tutp-demo --region=us-central1 --to-revisions=<revision>=100 --update-tags=pdftest=<revision>`. Exit code 0 only then.

Sixth check (approved, built as check 6): the NEW revision's own commit-sha label equals `<commit>` (otherwise check 5 and 1 are about a commit that is not what would go live).

## TUT-89: sharded e2e: finding that needs your decision

I checked which test families each spec signs in as. **Nearly every spec uses family 16 (mother 9999900001):** answer-explain, bonding, chips, dashboard-items, el, homework, img1, library, login, max-plan, singapore-maths, story, uploads, visual-tutor (and partners). Only family.spec.js uses mostly 04-07, and cache, cron, image-billing and inventory use none. So **grouping specs by the family they use cannot make two balanced shards**: almost everything is in one group.

Options:
- **A. Per-shard families (gives the ~half time).** Each shard signs in as its own set of test families (shard 2 = e.g. 9999900011.. as mother/father/member, plus its own family-B). Needs, outside the code: Firebase test phone numbers (code 123456), Supabase family rows marked `is_test`, and a TEST payment row per paid family (like family 16's, 365 days). In the repo: every spec's hardcoded `PHONES` reads an `E2E_PHONE_SET` env var (about 15 spec files, test code only). Your part: create the families and numbers; I print the exact list needed.
- **B. Shard only what is separable.** cache, cron, image-billing, inventory, family (own families) and partners go in shard 2 and everything on family 16 stays in shard 1. Needs no data work, but I estimate only about 25 % saved, not half. I will confirm from the per-spec times of the last CI run before you choose.
- **C. Do not shard.** Release-gate only.

My recommendation is A, built so that B works the day before the families exist (shard 2 falls back to the separable specs until `E2E_PHONE_SET=2` families are present).

Workflow design (any option): matrix job `shard` (fail-fast false, each shard its own `concurrency` is gone since shards must run together; the workflow-level group `e2e` stays so two dispatches never overlap), each shard runs the suite `RUNS` times on its own spec list, `tests/e2e/run.js` takes `E2E_SHARD=i/n` (a fixed list in the file, a test checks that every spec in `SPECS` is in exactly one shard). Final job `status` (needs: shard, `if: always()`) posts ONE commit status `e2e`, success only when every shard job succeeded (both runs, known failures allowed, spec row count per shard equals that shard's expected count). Permissions stay `statuses: write` and are held by the final job only. `known-failures.json` and `tests/e2e/recordings` are in the checkout of every shard, so each reads them unchanged. partners.spec.js runs in the shard that has its families free.

## What can go wrong

| # | Risk | Test that catches it |
|---|------|----------------------|
| 1 | Release gate prints the traffic command when a check failed (fail-open on an error, e.g. gcloud or gh returns nothing) | unit: every check fed an empty or errored fact returns FAIL and no command line; table test of all 2^5 pass/fail combinations: command only for all-pass |
| 2 | Live revision has no commit-sha label, or the label is a short sha git cannot resolve | unit: missing label = FAIL; unknown sha = FAIL; short sha that is an ancestor = PASS |
| 3 | Label commit is NOT an ancestor but is merely an equal or newer sibling (the 2026-10-22/23 mistake: main behind live) | unit: ancestor of itself PASS; sibling commit FAIL; live ahead of new FAIL |
| 4 | A secret or env name only on live is missed because it moved from plain env to secretKeyRef (same name, different source) | unit (built): a secret turned into a plain env value, or pointed at another secret name, FAILs check 2; a name only on live FAILs; names only on new are fine |
| 5 | Flag values differ in case or whitespace (`1` vs `true`), or one is absent | unit: equal PASS; `1` vs `true` FAIL (strict, no guessing); absent on one side FAIL; absent on both PASS |
| 6 | `E2E_REPLAY` present on the new revision (preview image sent to traffic) | unit: present with any value, even empty = FAIL |
| 7 | Commit status `e2e` is success on an older run but a later run on the same commit failed | unit: use the latest state per context (combined-status endpoint); `failure` after `success` = FAIL |
| 8 | A secret value reaches the screen, a log or the unit test output | unit: facts fixture contains a fake secret value; assert it never appears in script output; grep test that the script has no `--format=json` and no `secrets versions access` |
| 9 | New revision built from a different commit than `<commit>` (status checked on the wrong commit) | proposed check 6; unit: label != commit = FAIL |
| 10 | Two shards use the same family and collide (rows, quota counters, the free-limit 402 after 5 sessions) | test: every spec's family set is declared; a unit test fails if two different shards share a family; CI run shows no 402 or `already_registered` |
| 11 | A shard family has no TEST payment row, so homework hits the free limit | pre-run check in the shard job: each family of the shard answers `/me` as paid, else the shard fails before the suite starts |
| 12 | A spec missing from every shard (silently never run) or in two shards | unit: `SPECS` equals the union of shard lists, no overlap; row-count guard per shard (existing check, now per shard) |
| 13 | One shard fails or is cancelled but the final job posts success | final job `if: always()` reads `needs.shard.result`; unit-style workflow test: success only when result is exactly `success`; a skipped or cancelled shard = failure |
| 14 | Two statuses `e2e` (one from each shard) or a status posted by hand | only the final job calls the statuses API; grep test that no other step posts; CLAUDE.md rule below |
| 15 | Known failures stop working in a shard (path differs, file not in checkout) | each shard prints how many known entries it saw; unit: run.js with `E2E_SHARD` still reads `known-failures.json`; a known failure in shard 2 shows KNOWN, not FAIL |
| 16 | Replay recordings differ per shard or a recording key depends on spec order | recordings are read-only in the checkout; one shard's run of a spec produces the same replies as the full run (compare the RESULT of a spec run alone vs in the full suite); a `no_recording` 502 is MISSING RECORDING and fails that shard |
| 17 | Shards run on a preview that has `E2E_REPLAY` unset, and make paid calls | existing guard step stays in every shard; no `--live`/`--record-all` in the workflow (existing grep) |
| 18 | The preview server serves two shards at once and the 8 s model budget or memory trips (flaky timeouts) | compare pass/known set of a sharded run with the last unsharded run; any new FAIL is investigated, not retried |
| 19 | Total time does not drop (setup per shard, Chrome install, one slow spec) | report run time vs the old ~28 min; shard lists balanced from per-spec times of the last CI run |
